From issue to merge request, inside GitLab and GitHub

You label an issue and approve a plan. DAIV writes the code, opens the merge request, watches its CI and fixes failures, and answers review comments.

Security model

Each layer limits what a run can reach

DAIV acts on issues, comments and code that other people wrote. So the agent works in a sandbox, behind a network allow-list, without holding the credentials it uses.

{% icon "sandbox" "h-5 w-5 text-text-muted" %}

A sandbox per session

Every command the agent runs executes in a Docker container managed by daiv-sandbox, optionally under gVisor for a stronger boundary against container escape.

{% icon "lock-closed" "h-5 w-5 text-text-muted" %}

No network unless you allow it

The sandbox has no network by default. A sandbox environment can open it with an egress allow-list that blocks every other host; if the egress proxy is unavailable, the run aborts rather than falling back to an open network.

{% icon "key" "h-5 w-5 text-text-muted" %}

Credentials stay outside the container

A credential for an allowed host, such as a private registry token, is stored encrypted and added to matching requests by the egress proxy, so the agent never sees it.

{% icon "clock" "h-5 w-5 text-text-muted" %}

Short-lived, scoped git tokens

On GitLab, DAIV clones and pushes with a short-lived token scoped to one project (on GitLab.com this needs Premium or Ultimate, otherwise it uses its main token). On GitHub, it uses a short-lived installation token scoped to the one repository.

People stay in charge. On an issue, DAIV writes code only after someone approves its plan, and allowed_usernames in .daiv.yml limits who can trigger it. Prompt injection through an issue, a comment or repository content is still possible: these layers limit what an injected instruction could reach, not whether the agent reads one.
